# План: превращение блога в GitHub public template

Источник: [`prompts/promt-for-public-template.md`](prompts/promt-for-public-template.md)
Репозиторий: `https://github.com/alexchasx/laravel-orchid-blog` → шаблонный `laravel-blog-template`

**Цель:** любой разработчик может нажать «Use this template» и получить чистую основу для своего блога на Laravel + Orchid Platform, а не копию проекта со специфичными данными.

---

## 1. Очистить `.env.example`

Заменить все реальные значения на пустые или плейсхолдеры:

```dotenv
APP_KEY=
DB_DATABASE=
DB_USERNAME=
DB_PASSWORD=
SUB_LOGO=
```

- [ ] Убрать захардкоженные ключи, пароли, имена баз, пользовательские подзаголовки.
- [ ] Убедиться, что файл стал шаблоном конфигурации, а не копией боевого `.env`.
- [ ] Проверить остальные `APP_*` / `MAIL_*` / `MY_*` переменные на реальные значения (email, хосты) и при необходимости заменить плейсхолдерами.

## 2. Удалить lock-файлы

- [ ] Удалить `composer.lock` из репозитория.
- [ ] Удалить `package-lock.json` из репозитория.
- [ ] Добавить оба файла в `.gitignore`, если их там нет.
- [ ] Убедиться, что в новом проекте из шаблона зависимости ставятся свежие (`composer install` без lock).

## 3. Очистить миграции

- [ ] Найти в `database/migrations/` захардкоженные данные через `DB::table()->insert()` или аналоги.
- [ ] Перенести такие данные в сидеры (`database/seeders/`) или удалить.
- [ ] Миграции должны только создавать структуру таблиц.
- [ ] Проверить, что `migrate:fresh --seed` восстанавливает нужное стартовое наполнение (рубрики/теги/админ).

## 4. Удалить проектные файлы

- [ ] Удалить `_ISSUES.md`, `BACKLOG.md` и любые файлы, специфичные для проекта: заметки, todo, черновики, скрипты деплоя под конкретный сервер.
- [ ] Просмотреть корень и `docs/` на наличие личного/проектного мусора; решить, какие документы оставить (публичная документация шаблона).
- [ ] Проверить `screenshots/`, `tools/`, `.gigacode/`, `.gigacode_vsc/`, `.codeassistant/` — оставить только то, что нужно для шаблона.

## 5. Описать возможности («из коробки»)

Составить в README список того, что уже работает из коробки:

- CRUD постов (статьи), категории (рубрики), теги;
- медиа-загрузка (Orchid);
- роли и права доступа (Orchid);
- гостевые комментарии с математической капчей;
- форма обратной связи;
- подписка на новые статьи с рассылкой по email;
- автопубликация запланированных статей;
- Blade-фронтенд + админ-панель Orchid на `/admin`.

Отредактировать файл AGENTS.md.

## 6. «Что нужно поменять после создания» — задокументировать в README

- [ ] `APP_NAME`, `APP_URL` в `.env`;
- [ ] `SUB_LOGO` — подзаголовок сайта;
- [ ] название проекта в `composer.json` и `package.json`;
- [ ] favicon и логотип в `public/`;
- [ ] настройки Orchid в `config/platform.php`.

## 7. Обновить `composer.json`

- [ ] Изменить `name` на `alexchasx/laravel-blog-template`.
- [ ] Проверить `description`, `keywords`, `authors` — убрать личные данные при необходимости.

## 8. Обновить `package.json`

- [ ] Изменить `name` на шаблонный.
- [ ] Очистить проектные скрипты (деплой на конкретный сервер и т. п.), если есть специфичные.

## 9. Добавить `.gitattributes`

Создать `.gitattributes` с `export-ignore` для файлов, не нужных в новых проектах:

```gitattributes
.gitattributes export-ignore
.gitignore export-ignore
.editorconfig export-ignore
README.md export-ignore
```

- [ ] Дополнить список при необходимости (например, `Makefile`, папка `docker/` и другие — по решению).

## 10. Очистить публичные ассеты

- [ ] Проверить `public/` на специфичные файлы: favicon, логотипы, загрузки, скриншоты.
- [ ] Оставить только дефолтные файлы Laravel/Orchid.
- [ ] Кастомные логотипы заменить на placeholder или удалить.
- [ ] В README указать, что нужно добавить свои favicon и логотип.

## 11. Проверить config-файлы

- [ ] Проверить `config/platform.php` и другие конфиги на захардкоженные значения: URL сайта, имя проекта, email администратора.
- [ ] Заменить на дефолтные или на `env()` с пустым значением по умолчанию.
- [ ] Проверить `config/my_config.php` (сайт-специфичные `MY_GITHUB`, `MY_TELEGRAM`, `CONTACT_EMAIL`, `SUB_LOGO`, `SLOGAN`) — перевести на `env()`.

## 12. Финальная проверка

- [ ] В репозитории не осталось реальных паролей, ключей, токенов, email-адресов (кроме `admin@example.com` как дефолта).
- [ ] `php artisan key:generate` генерирует новый ключ (значение `APP_KEY` в `.env.example` пустое).
- [ ] После `composer install` + `migrate --seed` проект запускается с нуля без ошибок.
- [ ] В git-истории нет утечек: если раньше в коммитах были реальные `.env` файлы — добавить их в `.gitignore` и убрать из индекса через `git rm --cached`.
- [ ] Проверить, что сборка фронтенда проходит (`npm install` + `npm run build`) без lock-файлов.

---

## Порядок выполнения

1. Секции 1–4 (очистка) — базовая гигиена репозитория.
2. Секции 7–11 (метаданные, ассеты, конфиги) — приведение к шаблонному виду.
3. Секции 5–6 (README: возможности + что менять) — документация шаблона.
4. Секция 12 — финальный аудит перед публикацией как template.

> Примечание: проект работает только через Docker (`make` из `docker/docker-compose.yml`); проверки из секции 12 выполнять через `make setup` / `make test` внутри контейнеров, локальные php/composer/npm не используются.
