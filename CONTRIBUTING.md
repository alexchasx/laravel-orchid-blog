# CONTRIBUTING.md

Руководство для разработчиков, желающих внести вклад в проект **Laravel Orchid Blog** — русскоязычный пример блога на современных Laravel и Orchid Platform.

Спасибо, что помогаете проекту! Перед началом работы внимательно прочитайте этот документ, и по желанию:

- [`AGENTS.md`](AGENTS.md) — краткая памятка по проекту (команды, gotcha, договорённости);
- [`docs/architecture.md`](docs/architecture.md) — архитектура: слои, схемы, маршруты, особенности;

---

## 1. Язык

Весь код, комментарии, UI-копия, коммиты и документация ведутся **на русском языке**. Исключения — только технические термины и названия ассетов/классов.

Новые публичные функции могут относиться к одной из двух поверхностей (или к обеим): Blade-фронтенду или админ-панели Orchid. Определите правильную поверхность до начала работы.

## 2. Требования к окружению

- **Docker Engine** 24+ и **Docker Compose** (плагин `docker compose`)
- **Make** (для каноничных команд; без него — голый `docker compose`, см. README)

Проект запускается **только через Docker**: локальные PHP/Composer/npm/MySQL на хосте не используются.

## 3. Быстрый старт

Каноничный рабочий процесс — через `Makefile` (`make help` — список всех команд), **не** голые artisan/composer. Все команды выполняются внутри контейнеров по конфигурации `docker/docker-compose.yml`.

```bash
make install        # полная настройка: сборка + .env + composer/npm + key + migrate:fresh --seed + admin + storage:link + frontend
make up             # поднять контейнеры
make down           # остановить
make shell          # войти в контейнер app
```

Сайт: `http://localhost:8080`, админка: `http://localhost:8080/admin` (`admin@localhost.ru` / `123456`), phpMyAdmin: `http://localhost:8899`, MailHog: `http://localhost:8026`. Конфигурация — `docker/docker-compose.yml` (не в корне репозитория).

> ⚠️ `make migrate` (входит в `make install`) выполняет **`migrate:fresh --seed`** — команда **разрушает** базу данных. Не запускайте её на данных, которые нужно сохранить.

## 4. Рабочий процесс

1. Создайте ветку от `develop` (основная ветка разработки):
   ```bash
   git checkout develop
   git pull
   git checkout -b feature/краткое-описание
   ```
2. Внесите изменения, не забывая про договорённости из раздела «Код-стайл и договорённости».
3. Прогоните тесты и линтер (см. раздел «Проверка изменений»).
4. Откройте Pull Request:
   - опишите суть изменений и почему они нужны;
   - укажите, если меняли схему БД, маршруты или права доступа Orchid;
   - приложите скриншоты для изменений вёрстки (public) или экранов админки.

### Коммиты

- Формат сообщений — в стиле истории репозитория: краткое описание по-русски в повелительном наклонении (`добавил подписку на новые статьи`, `правки подписки и рассылки`).
- Не включайте в коммит мусор: файлы сборок, `.env`, кэш, `storage/`, логи.
- Перед коммитом убедитесь, что в diff нет секретов (ключей, паролей, токенов) — `.env` в репозиторий не попадает.

## 5. Код-стайл и договорённости

Проект следует стилю Laravel (Pint-конфигурации нет, `php -l` — единственный линтер). Обязательно учитывайте следующее:

- **Инвалидация кэша — только через model observers** (`ArticleObserver`, `RubricObserver`, `TagObserver`) и `Tag::updateCountArticles()`. Событийная модель (Events/Listeners) в проекте **не используется** — не добавляйте её.
- **Не «чините» колонку `excert`** (опечатка вместо «excerpt»). Она сохранена во всех слоях: `Article`, `ArticleService`, `ArticleResource`, шаблоны.
- Опечатка в названии — единственное такое исключение; свои поля/колонки называйте правильно.
- Ключи кэша (`Tag::SIDEBAR_CACHE_KEY`, `Rubric::SIDEBAR_CACHE_KEY`) живут на моделях.
- Модель `Article` автоматически генерирует `slug` и конвертирует markdown `content_raw` → `content_html` в `booted()` — не дублируйте эту логику в контроллерах.
- Middleware `GoogleRecaptcha` не подключён ни к одному маршруту. Если включаете его на формах — формы обязаны отправлять поле `r`, иначе 403.
- Laravel 13-стиль: маршруты и middleware регистрируются в `bootstrap/app.php`, `Http/Kernel.php` нет.
- Пользовательский ввод, выводимый через `{!! !!}`, допустим только для `content_html`, сгенерированного из markdown; прочий текст — через `e()` / `{{ }}`.
- В админке Orchid демо-экран (`example*`) — это заготовка из коробки; рабочая функциональность сосредоточена в `app/Orchid/Screens/`.
- **Комментарии в коде — только по-русски**, там, где они действительно нужны (без лишнего копипаста).

## 6. Проверка изменений

Перед отправкой PR обязательно выполните:

```bash
make test   # docker compose exec app php artisan test (PHPUnit, БД testing)
make lint   # php -l для всех .php в app, database, routes (внутри контейнера)
```

- Учетные данные/окружение для тестов — в `phpunit.xml` (запуск против БД `testing`); перед тестами БД `testing` должна существовать в MySQL-контейнере (см. `docs/testing-plan.md`).
- Если меняли схему БД — добавьте миграцию (без редактирования старых, если иного не требуют изменения).
- Меняли фронтенд — проверьте `make frontend-build` (сборка Vite внутри `blog_node`).
- CI в проекте нет — проверки локальные, на порядочности.

> Сейчас тесты — только boilerplate `ExampleTest`. План наполнения реальными тестами описан в [`docs/testing-plan.md`](docs/testing-plan.md): **новые тесты для доменной логики приветствуются** и опираются на этот план.

## 7. Отчёты об ошибках и предложения

- Для багов укажите: что ожидалось, что произошло, как воспроизвести, окружение (Docker, `docker/docker-compose.yml`, конфигурация `.env`).
- Для предложений опишите задачу и, если возможно, предлагаемое решение.
- Если правка затрагивает публичный дизайн — приложите скриншоты «до/после».
